# Dotclear modules conventions

Shared conventions of the Dotclear modules (plugins and themes) of [JcDenis](https://github.com/JcDenis),
written for humans and for AI assistants (Claude Code and others).

Other authors are welcome to use them as a base:

* **Part 1** applies to any Dotclear module.
* **Part 2** lists the choices of the author: adopt them or not.
* **Part 3** explains the files of a module for AI assistants and how they point to this file.

The file is read online: there is a single copy, always up to date, nothing to install or synchronize.
The `CLAUDE.md` of a module takes precedence over this file for that module.

---

## Part 1. Dotclear modules

### Repository

* One repository per module, named exactly like the module id, default branch `master`.
* At the root: `_define.php`, `README.md`, `CHANGELOG.md`, `LICENSE`, the code in `src/`, translations in `locales/`.
* `README.md` is shown alone on the module page of the Dotclear site: every link in it is a full URL
  (`https://github.com/<owner>/<module>/blob/master/...`), never a relative one.
* Links to the Dotclear repository of modules point to dotclear.org
  (`https://dotclear.org/plugin/detail/<id>`, `https://dotclear.org/theme/detail/<id>`), not to dotaddict.

### Code

* Dotclear 2.39+ API: `App::`, `My extends MyPlugin` (or `MyTheme`), `TraitProcess` (`init()`, `process()`, `render()`),
  `Dotclear\Helper\Html\Form` components, `declare(strict_types=1)` and typed code.
* **The code follows the Dotclear version required in `_define.php`** (`['core', 'x.y']`): no API newer than this version,
  and the new API of this version is used (a module published for Dotclear 2.40 uses the 2.40 methods).
  The module is checked and tested against this version.
* PHPStan level max with deprecation rules, against the required Dotclear version. No `@phpstan-ignore`, no baseline.
* Form components do not escape values: use `Html::escapeHTML()`.
* SQLite returns native int and float: read records with `MetaRecord` helpers (`intField()`…),
  and remember that `strField()` returns `''` for a number.
* Database table names in lower case, so they depend on no case rule of the database.
* Code must give the same result with MySQL, PostgreSQL and SQLite (for example, case and accent insensitive search
  done in PHP rather than in SQL).
* Data migrations on module update go in `src/Install.php`
  (`App::version()->getVersion(My::id())` and `version_compare()`).
* Public side: user sessions are handled by dedicated plugins (FrontendSession…). A module does not open
  its own PHP session on the public side.
* Dotclear must stay simple to install: no module may require a change of the web server configuration (Apache, nginx).

### Administration

* Admin pages stay consistent with the core admin:
  the page of the module shows the list, and a green button at the top right leads to the add form, on its own page;
  lists use the core `Filters` block ("Filters and display options") and the core actions on selected items.

### Translations and admin help

* Code, `_define.php`, README and CHANGELOG in English.
* French translation in `locales/fr/main.po`, with `locales/fr/main.lang.php` generated by `L10n::generatePhpFileFromPo`.
* Admin help (Dotclear help block), in English and French: one short help per admin page,
  `locales/{en,fr}/help/help.html` for the main page of the module and `locales/{en,fr}/help/<page>.html` for the others,
  registered in `locales/{en,fr}/resources.php` (`App::backend()->resources()->set('help', '<Module>-<page>', ...)`)
  and shown with `helpBlock(My::id() . '-<page>')`.
  A few `<dt>`/`<dd>` at most: the help panel is small. Check it in both languages.

### AI assistant connector (ClaudetteMcp)

[ClaudetteMcp](https://github.com/JcDenis/ClaudetteMcp) connects an AI assistant to a blog through MCP
(its design is in its `CONCEPTION.md`). A module that wants to give tools to the assistant:

* carries its own link, in its own code: classes in `src/ClaudetteMcp/` extending `Dotclear\Plugin\ClaudetteMcp\McpTool`
  (or `Tool\PostTool` for entries: `fetch()`, `editable()`, `canWrite()`), added with the behavior `ClaudetteMcpAddTool`
  in its `Frontend.php`, using its own classes (example: [periodical](https://github.com/JcDenis/periodical));
* never adds ClaudetteMcp to its `requires`: the module works without it;
* does not limit `Frontend::init()` to some URL types, or the behavior is never registered for the connector;
* checks the Dotclear permissions in each tool (tools run in frontend context, where the core checks nothing):
  a key never gives more than the permissions of its user;
* deletes nothing through the connector, touches no blog settings, users, plugins or keys;
* keeps the number of tools small: each tool is validated by the user when the connector is (re)connected.

### Testing

* Test admin pages, public pages, forms (with nonce), and check PHP warnings, on the Dotclear version required in `_define.php`.
  A module requiring a Dotclear version not yet released is tested on a Dotclear `master` checkout.
* Dotclear includes compiled templates with `@include`, which hides PHP errors of public pages:
  remove that `@` locally while debugging public pages.
* Local test site: Dotclear on SQLite with `php -S`, modules symlinked in `plugins/`.
  * Run it with `PHP_CLI_SERVER_WORKERS=4`: some pages call the site itself.
  * `Http::head()` sends an invalid header with the `cli-server` SAPI, which empties JSON responses:
    for local tests only, treat `cli-server` like `cgi` in `Http::head()`.
  * Dotclear may write a `_disabled` file in a module whose requirements are not met: remove it, never commit it.

## Part 2. Choices of the author

### Commits

Commit subjects start with **one tag**, in lower case, for the main effect of the commit:

| Tag | Use | CHANGELOG |
|---|---|---|
| `[new]` | new feature, tool, setting | yes |
| `[change]` | change of a behavior visible to users | yes |
| `[fix]` | bug fix | yes |
| `[security]` | security fix | yes |
| `[remove]` | removed feature or file | yes |
| `[compat]` | adaptation to a Dotclear version | yes |
| `[lang]` | new or reworked translations | yes |
| `[docs]` | addition or substantial change of the user guide or of the admin help | yes |
| `[refactor]` | code rewritten without change of behavior | yes |
| `[cosmetic]` | micro change without impact on the module: a wrong translation, a typo, README or CHANGELOG cleanup, TODO notes, `CLAUDE.md` and `CONCEPTION.md` | no |
| `[ci]` | workflows and tooling | no |

* Example: `[fix] Keep selected list after a search`, `[compat] Bump Dotclear from 2.39 to 2.40`.
* A commit without tag counts as `[change]`.
* The release workflow skips commits starting with `[cosmetic]` or `[ci]`; the other ones are written in the CHANGELOG as they are.
* The release commit is a single line `Release x`, without tag and without trailer.
* Commits are made under the author's identity (author and committer: his name and the e-mail of his GitHub account), also when an AI assistant writes them, without `Co-Authored-By` trailer. The assistant is credited in the `## CONTRIBUTORS` list of the `README.md` instead.

### Branches

* Update for a Dotclear version on a branch `update<version>` (example: `update2.39.3`).
* Issue fix on `fix-issue-<n>`, with a pull request "Fix #n".
* Small fixes go directly on `master` when the author says so.
* Merged branches are deleted by the workflow, on push to `master`.

### Versions and releases

* Versions are 1 to 3 numbers separated by dots, without letter or suffix (`2.5`, `1.2.3`, `2026.08.12`):
  the Dotclear repository refuses other versions.
* Date versions (`2026.08.12`) become the date of the day (Europe/Paris), so one release a day;
  other versions are incremented after the first dot and shortened (`2.4.1` → `2.5`, `1.9` → `1.10`).
* Releases are made by the [module workflow](https://github.com/JcDenis/gh2da/blob/master/README.md#dotclear-module-workflow) of gh2da:
  release button, CHANGELOG written from the commits since the last release, checks and tests, zip, Dotclear repository.
  Releases need checks and tests to pass.
* A CHANGELOG entry lists what changed for the user of the module, not the history of the work:
  before a release, commits that cancel each other, are internal or duplicate one change are squashed,
  or the entry is cleaned after the release in a `[cosmetic] Clean CHANGELOG` commit.
* Before a release, the user guide (`docs/fr/`), the admin help (`locales/{en,fr}/help/`) and the README are checked
  against the commits since the last release (new or changed features, settings, interface labels, screenshots).
  Outdated parts are fixed before the release, in a `[docs]` commit (`[cosmetic]` for a micro fix).
* Modules can also be published for the Dotclear version in development, to be tested on dotclear-dev installations.

### Tests by the module workflow

* Modules with a `_disabled` file are not tested.
* Extra pages to browse are listed in `.github/dotclear-test.txt` (`admin:...` / `public:...`).
* Required modules and modules used in code come from the same owner, then from `franck-paul/<id>`.

### Documentation

* User guide in French: `docs/fr/utilisation.md` (title « <Name> : guide d'utilisation », table of contents,
  one section per feature, short sentences), screenshots in `docs/fr/img/` with French names.
  Interface labels in the guide are checked on the real admin pages (in French).
* Screenshots: Dotclear on a local test site, viewport 1280, user in French with Europe/Paris timezone,
  realistic French example data, blog named « Mon blog », cropped to the useful part.
* The guide is linked from the README, with a full URL, in ABOUT and in LINKS (« User guide (in French) »).
* `docs/` is excluded from the release archive.

### AI assistants

* The Dotclear team allowed publishing modules made with an AI assistant. When an assistant modifies the code of a module,
  it is added as last entry of the `## CONTRIBUTORS` list of the README (for Claude: `* Claude (AI assistant by Anthropic)`).
* Each module has a short `CLAUDE.md`, and the modules with real design choices a `CONCEPTION.md` (see Part 3).

## Part 3. Files of a module for AI assistants

### `CLAUDE.md`: how to work in this repository

Read automatically by Claude Code at the start of each session in the repository, so it stays **short**
(under 100 lines, in English) and only holds what is specific to the module:

* what the module does, in two lines;
* a link to this file, to read first;
* its structure: tables, behaviors, classes, links with other modules;
* its known pitfalls and what not to touch;
* how to test it;
* a pointer to `CONCEPTION.md`, to read before changing the design.

No secret, no private address: repositories are public.
A model is in [`templates/CLAUDE.md`](https://github.com/JcDenis/gh2da/blob/master/templates/CLAUDE.md).

### `CONCEPTION.md`: why it is built this way

Not loaded automatically: read when the design is about to change. It is useful to humans too.

* goal and intended limits of the module;
* decisions taken, each with its reason and the options set aside;
* data model, permissions, tools given to the AI assistant;
* steps and ideas for later.

Only for modules with real design choices: a small widget does not need one.
Examples: [ClaudetteMcp](https://github.com/JcDenis/ClaudetteMcp/blob/master/CONCEPTION.md),
[PenseBete](https://github.com/JcDenis/PenseBete/blob/master/CONCEPTION.md).

### Keeping them up to date

* Both files are updated in the same work as the change: a change of structure or a new pitfall goes in `CLAUDE.md`,
  a change of design in `CONCEPTION.md`.
* A rule that would also apply to another module belongs in this file, not in a `CLAUDE.md`:
  a pitfall met again on a second module moves here and is removed from the module files.
  This file applies to all the modules: it is changed only with the author's agreement.
* Both files are excluded from the release archive, and committed as `[cosmetic]`.

### How the link works

A `CLAUDE.md` can only import local files (`@file.md`), not a web address. Each `CLAUDE.md` therefore asks the assistant
to read this file online, at `https://raw.githubusercontent.com/JcDenis/gh2da/master/CONVENTIONS.md`
(with `curl -s` from the shell if a web tool refuses the address).
Outside Claude Code, `CLAUDE.md` is not loaded automatically: the assistant reads it by hand before working on the module.

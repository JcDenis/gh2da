# Dotclear compatibility rules

`rules.json` lists what a module (plugin or theme) can meet in its code that breaks, or is deprecated,
from **Dotclear 2.39** to the **next Dotclear version** (the `master` branch of Dotclear): one comparison per version
(last tag of each branch with the next one, ex: 2.39.3 → 2.40.1 → master). A blog gets the rules newer than its own version.

It is meant for tools that check modules: the compatibility audit of DotclearWatch and DotclearWatchServer
(analysis on the blog, rules relayed by the server), a check in the CI of modules, or a quick look by an author.
The design of the audit is in the `CONCEPTION.md` of DotclearWatchServer.

* Generated by [`scripts/dotclear-rules.php`](https://github.com/JcDenis/gh2da/blob/master/scripts/dotclear-rules.php)
  from the sources of the last tag of each branch since `FROM_VERSION` (2.39, the oldest version supported by DotclearWatch)
  and of `master` (GitHub mirror of Dotclear), plus the manual rules of `rules-manual.json`.
* Updated every day by the workflow `.github/workflows/dotclear-rules.yml`, committed only when the rules change.
* Read it online: `https://raw.githubusercontent.com/JcDenis/gh2da/master/dotclear/rules.json`.

## Format

```json
{
    "dotclear": { "from": "2.39.3", "stable": "2.40.1", "next": "2.41-dev", "commit": "21096d880", "php_min": "8.2",
                  "steps": ["2.39.3 → 2.40.1", "2.40.1 → 2.41-dev"] },
    "rules": [
        {
            "id": "method:dcUtils::path",
            "type": "method",
            "symbol": "dcUtils::path",
            "since": "2.41",
            "level": "alert",
            "replace": "Path::reduce()",
            "note": "Method removed, was deprecated: since 2.28, use Path::reduce() instead"
        }
    ]
}
```

Header `dotclear`:

* `from`: first version compared; `stable`: last stable tag; `next`: version of `master` (`release.json`); `commit`: commit of `master`;
* `php_min`: minimum PHP version of the next version (`release.json` of `master`);
* `steps`: the comparisons made, oldest first.

Rule fields:

| Field | Content |
|---|---|
| `id` | Unique and stable: `<type>:<symbol>`. Used to replace or disable a rule by hand. |
| `type` | `class` (also interface, trait, enum), `method`, `property`, `const`, `function`, `behavior`, `js` and `php` (search of a `pattern`). |
| `symbol` | Fully qualified name, without leading `\`: `Dotclear\Core\Backend\Page`, `Class::method`, `Class::$property`, `Class::CONST`, behavior name; a short label for `js` and `php` rules (ex: `global $_ctx`). |
| `since` | Version (major.minor) where the change happens (`2.40`, `2.41` for master): the rule matters to a blog running an older version. A version later than the next one makes a forecast (ex: `2.45` while master is 2.41): counted as a notice until it becomes the next version. |
| `level` | `alert`: breaks with the next version. `notice`: deprecated or changed, breaks later or in some cases. |
| `replace` | What to use instead, when known (short text, may be empty). |
| `note` | Short explanation, in English. |
| `unique` | (methods) `true` when no class of the next version has a method with this name and the method is not static: a call found by its name alone (`->name(`) is then probably this one. Otherwise, only calls with a known class count (`Class::name(`, `parent::name(` in a subclass). |
| `pattern` | (`js` and `php` rules) PCRE pattern, without delimiters, searched with the `m` modifier: in `.js` and `.mjs` files for `js`, in PHP files without their comments for `php` (strings are kept, ex: `\$GLOBALS\['_ctx'\]`). |
| `manual` | `true` when the rule comes from, or was changed by, `rules-manual.json`. |

## What is generated

For each comparison (older tree → newer tree), with `since` the version of the newer tree. An element met in several comparisons
keeps the rule of the newest one (ex: deprecated in 2.40, removed in 2.41: an alert since 2.41).

Alerts:

* class, interface, trait or enum removed; its methods, constants and properties that were already deprecated get their own
  rule with the replacement read in their `@deprecated` comment;
* public or protected method removed, or no longer public/protected;
* method or function with more required parameters;
* public constant or property removed, or no longer public (promoted constructor properties included);
* function removed;
* behavior no longer called by the core.

Notices (newer tree):

* class, method, constant or function marked `@deprecated` (the replacement is read in the comment when written as `use …`);
* behavior flagged as deprecated (see `dotclear-behaviors.php`);
* method whose parameters changed without new required one: breaks the modules that override it,
  and calls in some cases (ex: 2.40 `WidgetsElement::setting()`, options moved to the 5th argument).

Methods, constants and properties are compared with traits and parent classes resolved:
a method moved to a trait or a parent class is not reported. Private elements are ignored.

Scanned: `src/`, `inc/` and `plugins/<id>/src/` of both trees (distributed plugins included, other modules use their API).

## What is not seen

Text analysis with the PHP tokenizer only, nothing is run:

* magic methods and properties (`__call()`, `__get()`, `func_get_args()`): ex. 2.40 `XmlTag::nodes()` renamed `getNodes()`;
* changes of behavior or of types without change of signature (ex. 2.40 `App::frontend()->search_count` became an `int`);
* JavaScript, CSS, templates, `DC_*` constants.

These go in `rules-manual.json`, by hand.

## Manual rules

`rules-manual.json` has the same `rules` list. Each rule is merged by `id`:

* a new `id` adds the rule (give all fields);
* the `id` of a generated rule replaces only the given fields (ex. a better `replace`);
* `"disabled": true` removes a generated rule (false positive).

Corrections of a single server (DotclearWatchServer) are made there, not here; a correction useful to everyone comes back here.

## Scanner

[`scripts/DotclearRulesScanner.php`](https://github.com/JcDenis/gh2da/blob/master/scripts/DotclearRulesScanner.php) checks a module
against the rules. One class, no dependency on Dotclear (PHP 8.2+), meant to be reused as is (DotclearWatch, CI of modules):

```php
$scanner = DotclearRulesScanner::fromFile('rules.json', '2.40.1'); // current Dotclear version: rules already applied are skipped
$report  = $scanner->scan('/path/to/module');                      // level (alert, notice, ok), files, alerts, notices, findings
$php     = $scanner->checkPhp(PHP_VERSION);                         // finding or null
```

Each finding gives the file, line, rule (`id`, `type`, `symbol`, `replace`, `note`, `since`), its `level`, `match` (`sure` or `probable`),
`context` (import, extends, implements, use, new, static, call, override, property, string, behavior, js, pattern), `guarded`
and `forecast` (rule of a version later than the next one: level lowered to notice).

From the command line, for one or more modules:

```bash
php scripts/dotclear-scan.php [--rules=<file or URL>] [--version=2.40.1] [--php=8.1.0] [--json] [--strict] <module directory>...
```

Without `--rules`, it reads `dotclear/rules.json` of the clone, else the online file. `--strict` exits with code 1 on an alert.

Test: `php tests/scanner/test.php` (fake module of `tests/scanner/module`, fixed rules of `tests/scanner/rules.json`,
expected findings in `tests/scanner/expected.txt`; `--update` rewrites them, check the diff).

How it reads the code:

* `vendor/`, `node_modules/`, `docs/`, `tests/` and hidden directories are skipped.
* A class and one of its members on the same line give one finding: the member when it has a replacement, else the class.
* A call by method name alone is ignored on `$this` and when the module declares a method with that name.
* Class names in strings count only when qualified (`'Dotclear\Core\…'`): a short one is often a plain word (`'form'`).
* Limits: a method called on a variable whose class is unknown is only found by its name (`unique`);
  the parents of core classes are not known (a rule on a core grandparent of a module class is missed).

## Reading the rules (for another scanner)

* Search PHP files with the tokenizer, resolve `use` imports, compare names case insensitively (as PHP does).
* `class`: any use of the name (`new`, `extends`, `implements`, static call, `instanceof`, type, `::class`, string in a `class_exists()`).
* `method`, `const`, `property`: `Class::name` on the class or a subclass; by name alone only when `unique` is `true`.
* `function`: call of the function (namespaced or global).
* `behavior`: string given to `addBehavior()` / `addBehaviors()`.
* `js`: `pattern` in `.js` and `.mjs` files; `php`: `pattern` in PHP files, comments removed (lines kept).
* A rule whose `since` is later than the next version (`next` of the header) is a forecast: report it as a notice.
* A module that already handles both versions (`class_exists()`, `method_exists()`, `version_compare()` on the Dotclear version)
  should see its alerts lowered to notices in the file concerned.

## Regenerate by hand

```bash
git clone --filter=blob:none https://github.com/dotclear/dotclear.git /tmp/dc
git -C /tmp/dc worktree add /tmp/dc-2.39 2.39.3
git -C /tmp/dc worktree add /tmp/dc-2.40 2.40.1
git -C /tmp/dc worktree add --detach /tmp/dc-next origin/master
php scripts/dotclear-rules.php /tmp/dc-2.39 /tmp/dc-2.40 /tmp/dc-next dotclear/rules-manual.json > dotclear/rules.json
```

Give two trees to compare two releases only (ex. `2.39.3` → `2.40.1`), for example to check the script against `CHANGES.md`.
